# Conclusions

This study compared several source content formats for a special-purpose RAG chatbot. In line with expectations, PDF proved to be a poor choice, and the tightly structured DITA format proved to be an excellent choice. However, HTML performed surprisingly poorly as a source format. 

With HTML, chatbot answers tended to be very good or very poor. One of these poor answers was analysed in detail, and the reason the RAG system failed for this question was related to the way the content was chunked and the lack of any overlap to mitigate the poor choice of chunk boundary.

Another weakness in the use of HTML in this study was that even after conversion to Markdown the source content retained a considerable amount of noise—principally side navigation text and Google Translate form text. This led to many chunks containing meaningless content and the Chroma database being twice as large as it was for plain text, PDF and DITA source. At the very least this would have impaired the efficiency of the RAG system.

HTML would probably have performed better if the conversion to Markdown had been smarter. It eliminated some noise content but left too much in place. In a real-life scenario it would be desirable to work with a cleaner, more RAG-friendly set of source HTML files that did not include all the extraneous ```nav``` and ```form``` content. Modern documentation systems provide such options, so this would be a sensible first step in preparing HTML content for RAG.

In a follow-up, I would need to gain a deeper understanding of splitter algorithms and test different chunking/overlap configurations. The results gained in this project, while informative on many levels, also prompt new questions and ideas for how to design more effective future experiments, and ultimately how to produce a RAG system reliable enough for general use.
