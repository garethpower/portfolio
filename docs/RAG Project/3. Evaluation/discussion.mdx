# Discussion

The table in [Output Data](output-data.mdx) presents the individual answer scores per question per source format/chunking configuration.

This chart visually represents the average scores across the configurations that were tested:

![Figure 1](/img/chart1.png)

## Numbers of Bad Answers

Scores of -2 are where egregiously bad answers occurred. In general, the RAG system had most trouble with questions targeting information contained in lists. One might have expected that it would have encountered as much difficulty, if not more, with questions targeting information in tables, but the scores do not bear this out. This may be because these the tables used in this study are relatively simple in layout.

The smallest number of bad answers occurred where DITA was the source format, and the second-smallest number occurred for Plain Text source format. Next was PDF.

By far the worst performer for bad answers was HTML, and its bad answers were predominantly on questions targeting information in lists and tables.

## Numbers of Excellent Answers

Plain text source was associated with the highest number of excellent answers (a score of 5), although DITA source was associated with almost as many, and overall produced more high scores than Plain Text. 

PDF source was associated with the lowest number of excellent answers.

Despite its overall poor showing, HTML source was also associated with a high number of excellent answers.

Although HTML source was associated overall with poor results, this was because of the highly polarized nature of the quality of the answers. HTML source produced large numbers of both excellent and very bad answers, with few answers of middling quality.

## Overall Average Answer Scores

Overall average answer scores were highest for DITA source, followed by Plain Text. PDF source was next. HTML average scores were slightly worse than those of PDF. 
There was a more even spread of answer scores for PDF compared to HTML.

## Effect of Chunk/Overlap Size

There was little indication that varying the chunk/overlap size affected the performance of the RAG system, except in the case of PDF. But even in this case a smaller chunk size that was associated with a higher score average. It seems likely that this is not a real effect, as smaller chunk sizes are generally associated with poorer context.

## HTML is the Poorest Performer

HTML performs very poorly in this study for questions targeting information in lists and tables. This is a surprising finding, because HTML’s structuredness compared to plain text and PDF ought to make it a superior source format.

In the light of HTML’s surprisingly poor performance as a source format, it makes sense to look more closely at how the chatbot went wrong.

HTML was the source format, and the RAG system was configured for medium-size chunks. The log records the question, answer and chunks that were used to contextualise the question.

Question 12 is asked, and the information vital to a correct answer is found in the “Relationship Attributes for a Contact” topic. 
The correct answer is that the Evaluator uses the following standards:
* Do you meet the RFP requirements?
* Have you met the defined criteria?
* Do you operate within our standards (such as Six Sigma)/company policy/business practices?

For every source format and chunk size, the chatbot yielded an acceptable answer to this question except for when HTML was the source format.
This part of the answer is not only wrong, but nonsensical:

```
They evaluate and accept based on defined standards, such as suggested targets and relationship attributes like Political Structure, Buying Role (for opportunity relationship maps), Decision Orientation (for account relationship maps), Support, and Coverage.
```

Chunk 1 shown in the sample above contains the definition of the Evaluator role, except that the chunk ends just when the standards are about to be listed. The next chunk, which was not selected for question contextualisation, listed the standards required for the correct answer. The splitter did not include an overlap between these two chunks, so the system did not detect the crucial connection between the chunks.

The reasons why the other chunks were selected to contextualise the question is not immediately obvious. The reference to “decision” in the question may have led to a similarity with some of them, or perhaps it is due to structural similarity, with these chunks defining roles or attributes in one way or another. The LLM may have detected that the first chunk was about to list something, so it took items that looked like list items from the other chunks, leading to a grossly inaccurate answer.

It seems clear that the lack of chunk overlapping led to the RAG system’s failure here.

For the HTML source used in this project, we must discount the first several chunks for each topic because they consist of noise content. 

Chunking seems in accordance with expectations until we reach the “Buying Role” chunk. From here, the splitter chunked a succession of tables mostly in accordance with the occurrence of table rows, which is the expected behaviour of the splitter when the table exceeds the chunk size upper limit.

However, the splitter failed to do this successfully for the crucial “Evaluator” row of the table.

## Splitting Algorithm for HTML and DITA

The manner in which the crucial HTML content was split led to question 12 being answered extremely poorly. For this reason, we need to look more closely at how the splitting algorithm – ```RecursiveCharacterTextSplitter``` – for HTML and DITA operates.

The algorithm tries to split the document into chunks smaller than the maximum allowed chunk size (if the document is not already below this size). To do this, it checks for each of the separators listed below in turn until it finds one that can split the text into chunks smaller than the upper limit size.

Headings get highest priority as they represent the breaks in the text most likely to preserve context.

(The splitter algorithm for Plain Text and PDF source content operates in the same way, but does not look for heading separators.)

| Separator | Description |
| --------- | ----------- |
| \n## | Markdown H2 heading |
| \n### | Markdown H3 heading   |
| \n#### | Markdown H4 heading   |
| \n\n | Paragraph break |
| \n | Line break |
| . | Full stop plus space (a sentence end) |
| “ “ | Single space (word break) |
| None | Character by character. This is the last resort. |

Overlaps are applied only when the chunks created are not along a natural contextual boundary. This is to prevent one context leaking into another. An overlap is applied only if the context continues from one chunk into the next.

This meant in practice that for many chunks there was no overlap. However, it does not explain why there was no overlap between the “Evaluator” chunk and the next chunk, because this is an obvious example of the context continuing from one chunk into another. 

It also remains unclear why this content was split in the first place, as the chunk size limit was not approached in this situation. It does not seem in accordance with the expected behaviour of the algorithm. In all other cases for the topic in question, chunking of table rows ended on desirable boundaries, or included an overlap where this was not possible.

This suggests that the reason why Question 12 was answered poorly is due to either a flaw in the algorithm or a behavioural subtlety I am not aware of. As it led to a bad outcome for the chatbot, the former seems more likely.
